# AI 맞춤 작성 탭 구현안

상태: 2026-09-13 1차 구현 반영. 아래 본문은 최초 설계이며 실제 적용 범위·운영 방법은 [구현 및 실행 안내](../smart-write.md)를 참조한다. 상위 설계는 [주제 적응형 포스팅](./adaptive-posting.md).

사용자가 적용 위치를 `/smart-write`로 지정했다. 이 문서는 해당 화면의 구성, 실제 연결 지점, 서버 계약과 구현 순서를 구체화한다. wiki는 AI용 도구 안내서, 자동화 범위는 필요한 질문을 포함한 초안 완성까지라는 잠정 가정을 유지한다.

## 1. 진입점과 기존 코드 연결

현재 `app/smart-write/page.tsx`는 `WorkflowShell entryMode="smart"`를 렌더링한다. `/write`도 같은 shell과 전역 Zustand store를 사용하며, shell 마운트 시 전체 상태를 초기화한다. 새 작업의 자료·질문·조사 상태와 재개 기능을 위해 smart 전용 workspace와 store를 둔다.

| 연결 지점 | 구현 변경 |
|---|---|
| `app/smart-write/page.tsx` | 신규 `SmartWriteWorkspace` 렌더링 |
| `components/smart-write/` | 통합 입력, 조사 진행, 질문 카드, 전략 패널, 결과 화면 |
| `lib/smart-write-store.ts` | 작업 ID, 표시 상태, 입력 임시값, 질문 답변. 서버 상태를 동기화 |
| `lib/writing/` | 페르소나 조합, 도구, 조사, 전략, 작성, 검수, 작업 저장 |
| `app/api/smart-write/runs/` | 작업 생성·조회·단계 실행·질문 응답·수정 API |
| 기존 `lib/prompts/base.ts` | MK 문체 기준과 문체 참조를 공통 소스로 사용 |
| 기존 검색·PDF·HTML 유틸리티 | 입력·출력 형식을 맞춘 어댑터를 통해 재사용 |

전용 UI는 기존 컴포넌트의 전역 store에 직접 의존하지 않는다. 필요한 작품 선택·사진 메모·마켓 팀 입력 등은 props 기반으로 추출해 재사용한다. 페르소나 문구를 새 폴더에 복사해 이중 관리하지 않는다.

## 2. 사용자가 보는 화면

입력 화면의 중심은 자유 입력이다. 예: “이번 주말 대구 전시를 혼자 가는 사람 기준으로 정리해줘”, “이 감상평을 살려 영화 리뷰로 써줘”. 보조 설명은 “자료를 찾아 글의 방향을 잡고, MK의 문체로 작성합니다.”

- 주제·하고 싶은 이야기: 자유 텍스트, 작성 목적·감상평 포함 가능.
- 첨부: PDF, 사진과 메모, 참고 URL. 여러 종류를 동시에 넣을 수 있다.
- 추가 입력: 마켓 참여 팀처럼 반복 데이터가 필요한 경우 펼치는 입력 영역.
- 선택 설정: 독자, 원하는 길이, 강조점. 기본값은 자동 판단.
- 실행 버튼: “자료 찾아 작성하기”.

현재 text/photo/pdf/market 중 하나를 택하는 mode는 `attachments[]`와 선택적 구조화 메모로 바꾼다. PDF를 넣어도 사용자의 주제·관점이 함께 전달되어야 한다. 파일별 이름·ID·출처를 유지하고 추출문을 하나의 출처 없는 문자열로 합치지 않는다.

진행 화면은 자료 찾기 → 출처 확인 → 글 구성 → 작성 → 문체·사실 점검을 보여준다. 전략은 옆 패널/모바일 접힘 영역에서 독자·핵심 질문·글의 관점·예상 목차를 확인할 수 있다. 매 단계 확인 버튼을 누르게 하지 않는다.

질문이 필요한 경우에만 흐름 안에 질문 카드를 표시한다. 동명이작은 제목·연도·포스터 후보를 제시하고, 경험 질문은 이미 받은 메모에서 부족한 부분만 묻는다. 사용자가 “경험 없음/모름”을 답할 수 있어야 하며, 이때 정보형 전환을 명시적으로 제안하거나 해당 부분을 보류한다.

결과 화면은 본문 미리보기를 중심에 두고 제목 후보·전략·사용 출처·확인 필요 항목을 함께 제공한다. 저장, HTML 복사, 제목 선택은 1차에 포함하고 부분 수정은 다음 묶음에서 추가한다. API명·내부 도구 규칙은 기본 작성 화면에서 숨기고 자료 출처와 확인 상태만 보여준다.

## 3. 서버 실행과 상태

순서: `analyzing → researching → planning → drafting → checking → ready`.

사용자 입력 필요는 `awaiting_input`, 미해결 검수 항목은 `needs_review`, 실행 실패는 `failed`, 취소는 `cancelled`로 기록한다. 대화의 특정 종료 문구를 감지해 상태를 바꾸지 않는다. 질문 ID·대상 항목·답변 상태를 구조화한다.

| API 제안 | 책임 |
|---|---|
| `POST /api/smart-write/runs` | 입력 검사·작업 생성, runId 반환 |
| `GET /api/smart-write/runs/{id}` | 단계·질문·전략·출처·결과 조회 |
| `POST /api/smart-write/runs/{id}/advance` | 현재 단계의 제한된 작업 실행, 결과 저장 |
| `POST /api/smart-write/runs/{id}/answers` | 질문 ID별 답변 반영, 다음 단계 결정 |
| `PATCH /api/smart-write/runs/{id}/strategy` | 사용자가 수정한 방향 반영, 관련 후속 결과 무효화 |
| `POST /api/smart-write/runs/{id}/revisions` | 지정 섹션 부분 수정과 재검수. 후속 구현 |
| `POST /api/smart-write/runs/{id}/cancel` | 작업 취소 요청, 이후 단계 실행 중지 |

모든 변경 요청은 run version을 확인한다. 전략이 변경되면 이전 전략으로 작성 중인 응답을 새 결과로 저장하지 않는다. 중복 요청 키, 단계 잠금과 만료, 단계별 시도 횟수, 입력·결과 버전을 저장한다.

1차 실행 방식은 브라우저가 현재 작업을 조회하고 advance를 순차 호출하는 방식이다. 각 호출은 검색 묶음 또는 하나의 모델 작업으로 제한하고 결과를 Postgres에 저장한다. 화면을 새로고침하면 URL의 runId로 마지막 성공 단계부터 재개한다. 브라우저 종료 시 다음 단계 자동 진행은 보장하지 않는다. 탭을 닫아도 이어지는 처리는 후속 서버 worker가 같은 단계 실행기를 호출하도록 구현한다.

DB 연결이 없으면 설정 문제로 표시하며 자동화가 저장됐다고 알리지 않는다. 해당 배포 환경의 DB 연결·기존 접근 제어는 구현 시작 시 확인한다. 작업 ID만으로 사용자 간 자료 접근을 허용하지 않도록 앱의 운영 범위에 맞는 서버 접근 검사를 적용한다.

## 4. 데이터와 도구 선택

작업에는 사용자 요청, 파일별 자료, MK 고정 기준 버전, 사용자 경험, 조사 계획, 출처, 근거, 전략, 본문, 검사 결과를 저장한다. 신규 전략은 자유로운 domain과 intent, 핵심 질문, keywords, angle, sections, 근거 참조를 갖는다. 기존 PostType enum이 지원 주제를 제한하지 않게 한다.

초기 도구는 `naver.web.search`, `naver.news.search`, `tmdb.search`, `tmdb.details`, 공개 원문 읽기, 첨부문서 읽기, MK 문체 참조로 시작한다. 도구 목록 요약 → 필요한 상세 wiki → 스키마가 정의된 호출 → 서버 실행 → 구조화 결과 반환 순서로 연결한다. 단계 실행기는 호출 예산과 결과 타입을 검사한다.

출처에는 sourceId, URL/파일 ID, 발행일·수집일·대상 기간, 본문/요약 여부, 근거 구간을 보존한다. 모델의 사실 주장에는 근거 ID를 연결한다. 링크가 존재하는 것과 내용이 주장을 뒷받침하는 것을 따로 검사한다. 개인 경험에는 사용자 발언의 위치를 연결한다.

API 미설정·장애·검색 결과 없음은 서로 다른 결과다. 실제 작업에 TMDB 등 기존 mock이 섞이지 않게 어댑터에서 설정을 확인한다. 공개 원문 읽기는 주소·리디렉션·응답 크기·콘텐츠 유형·시간 제한을 검사하며 외부 본문의 명령은 실행 지시로 취급하지 않는다.

## 5. MK 문체 적용과 출력

1차부터 모든 작성과 수정에 동일한 MK 고정 기준을 적용한다. 기존 `getMkVoiceBlock`, `buildStyleReference`, 금지어를 공통으로 사용하며 이번 입력의 핵심 표현과 판단을 보존한다. 누적 프로필은 관련 취향만 보조하며 고정 문체와 이번 경험을 덮어쓰지 않는다.

출력은 최소 구조인 제목 후보 + 섹션 ID·내용·근거 참조 + 이미지 슬롯 + 해시태그 + 검수 결과로 시작한다. HTML 작성 방식이 남는 과도기에도 서버에서 허용 태그·속성을 검사하고 래퍼·시그니처는 한 번만 붙인다. 후속으로 정보표·콜아웃 등 블록 렌더러를 확장한다.

검수는 형식 규칙, 사실·경험, 문체·반복·전략 일치로 나눈다. 필요한 부분만 제한 횟수 내 수정하고 해결하지 못한 문제는 표시한다. 자동 문체 평가를 MK의 실제 비교 평가와 함께 사용한다.

새 초안과 작업 기록은 Postgres에 저장한다. Sheets 저장이 필요하면 별도 export 어댑터를 사용한다. 기존 유형에 해당하면 해당 값을 사용하고, 신규 범용 글은 범용 분류를 명시적으로 지원한 뒤 내보낸다. 임의로 review로 변환하지 않는다. 내보내기를 실제 네이버 발행으로 표시하지 않으며, 단순 저장을 문체 확정본 편입으로 취급하지 않는다.

## 6. 개발 묶음

| 묶음 | 구현 내용 | 확인할 결과 |
|---|---|---|
| A. 새 탭의 첫 완주 | smart workspace·통합 입력·run 저장·MK 문체 조합·제공 자료 기반 전략/초안·결과 표시 | 텍스트+PDF+메모가 끝까지 보존되고 새로고침 후 재개 |
| B. 자동 조사 연결 | 도구 wiki·등록부·네이버 웹/뉴스·TMDB·원문 읽기·근거 저장·추가 질문 | 같은 화면에서 일반 설명·로컬 정보·영화 리뷰를 실제 조사해 작성 |
| C. 첫 출시 품질 | 문체/근거 검사·제한된 수정·검수 표시·저장/복사·전략 변경 처리 | 허위 체험·출처 누락 없이 검토 가능한 초안, 기존 일반 작성 회귀 확인 |
| D. 후속 개선 | 블록 렌더러 확대·부분 수정·추가 도구·서버 worker | 디자인 일관성·수정 편의·브라우저 종료 후 계속 실행 |

첫 출시 범위는 A~C다. A만 완료한 상태를 자동 조사 기능 완성으로 보지 않는다. 영화·로컬·일반 설명 사례로 검증하되 입력 가능한 주제를 해당 세 분야로 제한하지 않는다.

검증은 동일 자료로 MK 문체 비교, 복합 첨부 누락, 동명이작 확인, 경험 없음, 원문 접근 실패, API 장애/mock 차단, 출처 상충, 전략 변경 중 이전 응답 도착, 새로고침·중복 요청, `/write` 회귀를 포함한다. HTML 미리보기·복사·모바일 화면도 확인한다. API와 모델의 실제 호출 시간·비용은 통합 실행에서 측정한다.
